規則文本與機械閘門

開發者不該被指令遵守的虛假安全感騙

開發者習慣把約束寫進 AGENTS.md、.cursorrules 或專案規則文件，誤以得這樣 AI 代理就會「遵守」。本文經過數個月對 AI 代理行為約束的觀察與文獻回顧，提出一個核心區分：規則文本只是提示（steering），而非失效安全（fail-closed）約束；模型可以忽略它，尤其在長對話中更脆弱。 真正能擋住危險動作的，必須是模型外部的機械閘門——工具層級的預檢鉤子、拒絕代碼與失效安全設定。結論：規則負責溝通意圖，閘門負責兌現約束。開發者不該以「已寫規則」當作系統已安全的證明。

一、這個錯覺從哪裡來

很多團隊在專案根目錄放了一份 AGENTS.md，裡面列著「不要刪除生產資料庫」「結帳前必須確認金額」「變更核心邏輯前先跑測試」等條文。接著，開發者對 AI 代理下達指令，期待它因為讀到這些規則而自動遵守。

這個直覺看起來合理：人類看到規則會遵守，那麼讀到規則的模型應該也會。但實際觀察顯示，這是一種虛假安全感。開發者以為系統已經被約束，實際上規則文本只是擺在那裡的文字，沒有任何機制能在模型決定「不照做」時阻止它。

更糟的是，這種錯覺往往在出問題之後才被發現——代理已經執行了被禁止的動作，而事後檢查只剩下一個「PASS」的自報文字，並沒有對應的機械擋板。

二、規則文本不是約束：來自工具廠商的官方說明

主流 AI 編碼工具（如 Cursor）的官方文件已經明確說明規則文本的本質：AGENTS 與專案規則是「導向」（steering），不是「約束」（enforcement）。模型可以看到規則，也可以選擇忽略；在長對話中，遵守程度會進一步下降。

社群實證也指向同一個結論。有開發者在工具論壇回報：「PASS 只是模型生成的文字，不是機械檢查。」客服人員也確認：規則存在於模型提示詞中，是對模型的強烈建議，但不等於運行時的強制封鎖。換句話說，「模型說它已經遵守規則」這句話本身，只是模型生成的一段文本，沒有任何外部證據支持它真正執行了什麼。

這裡需要記住一個關鍵差異：

  • 規則層（Rules / AGENTS.md）：寫給模型看的自然語言，屬於提示詞的一部分，模型可遵可不遵，屬於機率性引導。
  • 機械層（Mechanical gate）：寫在模型外部的執行邏輯，如工具預檢鉤子（hooks）、拒絕代碼（exit code 2 / deny）、失效安全開關（fail-closed），模型無法單方面繞過。

開發者容易把兩者混為一談，以為寫了規則就等於裝了閘門。實際上，前者只是一張貼在牆上的告示，後者才是門上的鎖。

三、長對話裡，記憶會衰減

即使開發者真的很希望模型遵守規則，長對話本身也在對抗這個目標。多項研究顯示，大型語言模型在多輪對話中的指令遵守能力會明顯下降：所有受測模型在多輪設定中的表現皆低於單輪，平均下降幅度約達 39%；問題不在於模型「變笨」，而在於「不可靠性」大幅提升——模型容易在早期輪次下錯誤假設，之後便無法自行糾正，越走越偏。

具體表現包括：

  • 過早給出答案：模型在還沒拿齊所有資訊前就急著給出完整方案，之後新增需求時，它不會捨棄早期錯誤假設，只會在錯誤之上繼續堆砌，導致輸出越來越臃腫。
  • 中段遺漏：模型對開頭與最近一輪的關注度較高，對對話中段引入的約束容易視而不見。
  • 零溫度也無效：即使將生成溫度設為 0，單輪變得確定性，多輪對話中早期的一個微小偏差仍會 cascading 放大，不可靠性依然很高。

這意味著：哪怕 AGENTS.md 被載入上下文，在長對話進行到後段時，模型對「不能做什麼」的記憶也可能已經模糊。規則文本越長、對話越長，這個風險越大。

四、什麼是機械閘門

與規則文本不同，機械閘門不依賴模型的記憶或意願，而是在動作執行前由系統外部強制檢查。以 AI 編碼工具的工具鉤子（hooks）為例，它們可以攔截 Shell 執行、檔案寫入、編輯等動作，並在不符合條件時直接封鎖。

官方文件對封鎖行為的定義很清楚：鉤子腳本退出代碼為 0 表示允許，退出代碼為 2 表示封鎖該動作；其他非零代碼預設為「失效開放」（fail-open，動作照行），除非顯式設定失效安全（fail-closed）。這告訴開發者一個殘酷事實：預設狀態下，鉤子腳本出錯並不會阻止危險動作，開發者必須主動設定失效安全，閘門才會真正閉合。

社群另一個實證也值得注意：有開發者把鉤子設為「詢問使用者」（ask），希望危險指令執行前先暫停等人工確認。但在「自動審查」模式下，工具會直接判定指令安全並執行，鉤子的「詢問」會被忽略，不會彈出確認視窗。只有「拒絕」（deny）在所有模式下都被強制執行。換言之，軟性的「請先問我」在自動化場景下可能根本沒作用，只有硬性的「不准執行」才有效。

總結機械閘門的三個必要條件：

  1. 位於模型之外：檢查邏輯不在模型內部，模型無法藉由說服自己來繞過。
  2. 失效安全：腳本出錯、網路斷開或設定遺漏時，預設應封鎖而非放行。
  3. 拒絕才生效：「詢問」「建議」「提醒」都不可靠，關鍵動作必須用「拒絕」封鎖。

五、實務建議：分層防禦，閘門放在可執行動作前

基於以上觀察，對於部署 AI 代理的團隊，建議採取以下分層做法：

第一層：規則文本，只負責溝通意圖。
AGENTS.md 與專案規則繼續寫，但定位為「團隊共識文件」與「提示詞輔助」，不當作安全邊界。規則應簡短、具體，避免冗長條文讓模型在長對話中遺漏。

第二層：機械閘門，負責兌現約束。
將「絕對不能做」的動作（如刪除資料庫、修改生產設定、將金鑰寫入程式碼）寫成工具鉤子，在動作執行前攔截，使用拒絕代碼封鎖，並顯式開啟失效安全設定。閘門訊息應直接告訴開發者下一步該做什麼，而不只是說「被封鎖」。

第三層：人工驗收，不接受自我證明。
模型聲稱「已完成且符合規則」不構成證據。交付物必須由人類或獨立腳本重新檢查，特別是與安全邊界相關的變更。事後日誌與檢查點比模型的自報更可信。

六、結語

規則文本寫得再漂亮，也只是文字。模型可以忽略它、遺忘它、或在生成「PASS」後繼續做被禁止的事。真正的約束必須長在執行路徑上，由模型外部的機械閘門強制封鎖。

開發者不該以「已寫規則」當作系統已安全的證明。PASS 只是文字，不是檢查；閘門才是鎖。
