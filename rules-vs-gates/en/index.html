Rule Text and Mechanical Gates

Developers Should Not Be Fooled by the False Sense of Security of Instruction-Following

Developers habitually write constraints into AGENTS.md, .cursorrules, or project rule files, mistakenly believing that this will make an AI agent "comply." Drawing on several months of observation of AI agent behavior constraints and a literature review, this article proposes one core distinction: rule text is only steering, not a fail-closed constraint; the model can ignore it, and compliance becomes even more fragile in long conversations. What can actually block dangerous actions must be a mechanical gate outside the model — tool-level pre-check hooks, deny codes, and fail-closed settings. Conclusion: rules communicate intent; gates enforce constraints. Developers should not treat "the rules are written" as proof that the system is safe.

I. Where This Illusion Comes From

Many teams place an AGENTS.md in the project root, listing clauses such as "do not delete the production database," "confirm the amount before checkout," and "run tests before changing core logic." Then the developer issues an instruction to the AI agent, expecting it to comply automatically because it has read these rules.

The intuition seems reasonable: humans see rules and follow them, so a model that reads the rules should too. But actual observation shows this is a false sense of security. The developer believes the system is already constrained, when in fact the rule text is just words sitting there — no mechanism can stop the model once it decides "not to comply."

Worse, this illusion is often discovered only after something goes wrong: the agent has already performed a prohibited action, and the post-hoc check leaves behind only a "PASS" self-reported by the model, with no corresponding mechanical blocker.

II. Rule Text Is Not a Constraint: Official Statements from Tool Vendors

The official documentation of mainstream AI coding tools (such as Cursor) already states clearly what rule text really is: AGENTS and project rules are "steering," not "enforcement." The model can see the rules and can also choose to ignore them; in long conversations, compliance drops further.

Community evidence points to the same conclusion. A developer reported on a tool forum: "PASS is just text generated by the model, not a mechanical check." Support staff also confirmed: the rules exist in the model's prompt as a strong suggestion to the model, but they are not equivalent to a runtime hard block. In other words, "the model says it has complied" is itself just a piece of model-generated text, with no external evidence that it actually did anything.

One key distinction to remember here:

  • Rule layer (Rules / AGENTS.md): natural language written for the model to read, part of the prompt; the model may or may not comply — probabilistic guidance.
  • Mechanical layer (Mechanical gate): execution logic written outside the model, such as tool pre-check hooks, deny codes (exit code 2 / deny), and fail-closed switches, which the model cannot unilaterally bypass.

Developers easily conflate the two, assuming that writing rules is the same as installing a gate. In reality, the former is only a notice posted on the wall; the latter is the lock on the door.

III. In Long Conversations, Memory Decays

Even if developers genuinely want the model to follow the rules, the long conversation itself fights against that goal. Multiple studies show that the instruction-following ability of large language models drops noticeably in multi-turn conversations: all tested models performed worse in multi-turn settings than in single-turn, with an average decline of about 39%. The problem is not that the model "gets dumber," but that its "unreliability" rises sharply — the model tends to make wrong assumptions in early turns and then cannot correct itself, drifting further and further off course.

Concrete manifestations include:

  • Answering too early: the model rushes to give a complete solution before it has all the information; when new requirements arrive later, it does not discard its early wrong assumptions but piles more on top of the error, making the output increasingly bloated.
  • Mid-conversation omission: the model pays more attention to the beginning and the most recent turn, and easily overlooks constraints introduced in the middle of the conversation.
  • Zero temperature does not help: even setting generation temperature to 0 only makes a single turn deterministic; in a multi-turn conversation, one tiny early deviation still cascades and amplifies, and unreliability remains high.

This means: even if AGENTS.md is loaded into context, by the later stages of a long conversation the model's memory of "what not to do" may already be blurred. The longer the rule text and the longer the conversation, the greater this risk.

IV. What Is a Mechanical Gate

Unlike rule text, a mechanical gate does not depend on the model's memory or willingness; it is enforced by checks outside the system before an action executes. Take the tool hooks of AI coding tools as an example: they can intercept Shell execution, file writes, edits, and other actions, and block them directly when conditions are not met.

The official documentation is clear about blocking behavior: a hook script exit code of 0 means allow, exit code 2 means block the action; other non-zero codes default to "fail-open" (the action proceeds) unless fail-closed is explicitly set. This tells developers a harsh fact: by default, a hook script that errors out does not stop dangerous actions; developers must actively configure fail-closed for the gate to actually close.

Another piece of community evidence is worth noting: a developer set a hook to "ask the user," hoping to pause for human confirmation before a dangerous command runs. But under the "auto-review" mode, the tool directly judges the command safe and executes it — the hook's "ask" is ignored, and no confirmation window pops up. Only "deny" is enforced in all modes. In other words, a soft "please ask me first" may not work at all in automated scenarios; only a hard "do not execute" is effective.

To sum up, a mechanical gate has three necessary conditions:

  1. Outside the model: the check logic is not inside the model, so the model cannot bypass it by convincing itself.
  2. Fail-closed: when the script errors, the network drops, or a setting is missing, the default should be to block rather than allow.
  3. Only "deny" works: "ask," "suggest," and "remind" are all unreliable; critical actions must be blocked with "deny."

V. Practical Advice: Layered Defense, with Gates Placed Before Executable Actions

Based on the observations above, teams deploying AI agents are advised to adopt the following layered approach:

Layer 1: Rule text, responsible only for communicating intent.
Keep writing AGENTS.md and project rules, but position them as a "team consensus document" and "prompt aid," not as a security boundary. Rules should be short and specific, avoiding verbose clauses that the model will overlook in a long conversation.

Layer 2: Mechanical gates, responsible for enforcing constraints.
Write "absolutely must not do" actions (such as deleting a database, changing production settings, or writing keys into code) as tool hooks that intercept before execution, block with deny codes, and explicitly enable fail-closed settings. Gate messages should tell developers the next step directly, rather than merely saying "blocked."

Layer 3: Human acceptance, no self-certification accepted.
A model claiming "done and rule-compliant" is not evidence. Deliverables must be re-checked by a human or an independent script, especially changes related to security boundaries. Post-hoc logs and checkpoints are more trustworthy than the model's self-report.

VI. Conclusion

However elegantly rule text is written, it is still just words. The model can ignore it, forget it, or keep doing prohibited things after generating a "PASS." Real constraints must live on the execution path, forcibly blocked by a mechanical gate outside the model.

Developers should not treat "the rules are written" as proof that the system is safe. PASS is just text, not a check; the gate is the lock.
